# Using docs from Huntaway

[Huntaway](https://github.com/dire-kiwi/huntaway) is a kanban board where each task is worked by its own agent. Agents on it publish documents with a `docs` MCP server, and people read them on the board. Huntaway can also publish them on to a hosted docs site such as https://docs.nest.dire.nz, where they can be shared and commented on.

There are two parts:

1. **The board's own `docs` MCP server.** Every agent run gets it. Documents are stored on the Huntaway host, under the profile of the run's task, and shown on the board's **Docs** page.
2. **Publishing to a hosted site.** From the **Docs** page, a person connects the profile to a docs site and publishes a document's version there.

[Components](components.mdx) shows every MDX component a page can use.

## For agents: the `docs` MCP server

Each run has an MCP server named `docs`. In Claude Code its tools are `mcp__docs__<tool>`, and in Codex `docs.<tool>`. The tools run without a permission prompt.

| Tool | What it does |
|------|--------------|
| `publish_document` | Create a document or publish a new version of one. Pass `pages` (`{ path, content, format?, title? }`) and optionally `slug`, `title` and `message`. `mode: "merge"` keeps the previous version's other pages, and `delete_paths` drops some of them. |
| `list_documents` | The profile's documents, with each one's latest version and URL. |
| `get_document` | A document's pages (paths, titles, URLs) and its version history. |
| `read_page` | The Markdown/MDX source of one page, from the latest version or a given `version`. |
| `list_components` | Reference for the MDX components (callouts, details, form fields). |

They are the hosted server's tools, with the same schemas, checks, errors and warnings, because Huntaway runs the same renderer ([`@dire-kiwi/docs-render`](https://github.com/dire-kiwi/docs/blob/main/crates/docs-render-wasm/README.md)). A page that publishes on the board publishes the same way on the hosted site.

<Callout type="warning" title="What's different on the board">

- **No feedback or sharing yet.** `get_feedback` and `share_document` aren't there. Form fields (`<Approval />`, `TextInput` and the rest) render read-only and collect no answers, so ask the user for a decision in the task's thread instead (Huntaway's `request_user_input`).
- **Documents belong to the profile** of the run's task, not to a docs-site user. Slugs are unique per profile.
- **URLs point at the board:** `<board>/docs/<profile id>/d/<slug>/`, with `-/v/<n>/` for a version. `<board>` is the host's _Public URL_ setting, or else its own address.

</Callout>

<Callout type="tip">
  Always give the user the URL that `publish_document` returns, rather than leaving a write-up only in a message or a file.
</Callout>

### Publishing a document

A single-page report:

```json
{
  "title": "DOC-8: what changed",
  "message": "First draft",
  "pages": [{ "path": "index", "content": "# What changed\n\n..." }]
}
```

<Details summary="A plan with a nested menu">

`index` is the landing page, `plan/index` is the page for the `plan` folder, and relative links work as they do between files:

```json
{
  "slug": "rollout-plan",
  "pages": [
    { "path": "index", "content": "# Rollout\n\nSee [phase 1](plan/phase-1.md)." },
    { "path": "plan/phase-1", "content": "# Phase 1\n\n..." },
    { "path": "plan/phase-2", "content": "# Phase 2\n\nBack to [the overview](../index.md)." }
  ]
}
```

</Details>

<Details summary="Revising one page and keeping the rest">

Publish again with the same `slug` and `mode: "merge"`:

```json
{
  "slug": "rollout-plan",
  "mode": "merge",
  "message": "Phase 2: add the rollback steps",
  "pages": [{ "path": "plan/phase-2", "content": "# Phase 2\n\n..." }]
}
```

</Details>

<Details summary="Images">

Pass images in `images` and refer to them by name, or inline them in a page as `data:image/png;base64,...` URIs:

```json
{
  "slug": "benchmarks",
  "pages": [{ "path": "index", "content": "# Results\n\n![Throughput](images/throughput.png)" }],
  "images": [{ "name": "images/throughput.png", "data": "iVBORw0KGgo..." }]
}
```

PNG, JPEG, WebP, GIF (first frame) and AVIF work; SVG doesn't (export it as PNG). Every image is converted to AVIF, and only the AVIF is kept, not the original. Each must be at most 500 KB (512,000 bytes) after conversion, or the publish is rejected with the image's size: downscale or crop big screenshots and photos. Image data doesn't count towards a page's size. With `mode: "merge"`, the images of the pages you keep stay; you only send new or changed ones.

</Details>

Every publish creates a new version, and older ones stay readable, so revising is cheap. Use `"format": "mdx"` (or a `.mdx` path) for [components](components.mdx).

### Finding components

Plain Markdown (headings, lists, tables, code) needs no reference. For components, call `list_components`: it returns each component's name, props and an example, and for form fields the shape of the answer. [Components](components.mdx) shows the same reference rendered.

### Checking pages

`publish_document` is the check. A page it can't publish (broken MDX, a duplicate path, a page that's too large, an image that's over 500 KB as AVIF) is rejected with the reason, and no version is made. A page it can publish comes back with its URL and any warnings, such as an unknown component or a bad prop. Fix them and publish again; a new version costs nothing.

<Callout type="warning" title="Don't check pages with npm">
  Don't install or run `@dire-kiwi/docs-render`, a Markdown linter or any other tool to check a page. The MCP server runs the same renderer, so `publish_document` already gives the answer that counts.
</Callout>

### Using a sub-agent

The components reference and a document's pages are long, and the agent working the task rarely needs them once the document is out. If the agent can start sub-agents (Claude Code's Agent tool, for example), it hands the document to one:

1. The main agent gives the sub-agent what the document should say: the findings, the plan, the decision it needs.
2. The sub-agent calls `list_components` if it wants components, writes the pages, publishes them, and fixes any warnings.
3. It returns only the URL, which the main agent gives to the user.

The hosted server's instructions ask agents to work this way, so they do it without being told. The board's `docs` server has its own instructions, which are to say the same (HA-288).

## For people: the board's Docs page

Under the profile's **Assistant**, **Docs** lists the profile's documents with their latest version, when each was updated, and the task that published it. A document opens at `/docs/<profile>/d/<slug>/`, with its menu, the page and a version picker. A task's thread links each document it published.

### Publishing to a hosted docs site

1. On **Docs**, choose **Connect to hosted docs**. The site defaults to https://docs.nest.dire.nz.
2. Choose **Sign in**. The board shows a code and a link. Open the link, sign in, check that the code matches, and choose **Allow**. This is the OAuth device flow described under [Server-side clients](https://github.com/dire-kiwi/docs/blob/main/README.md#server-side-clients-device-flow). The client's name is Huntaway's own. Alternatively, paste a personal access token from the site's **Access** page.
3. Open a document and choose **Publish**. This publishes the version shown, with all its pages, its title and its message. The first time, it asks for the slug on the site (the local one by default). After that, each publish adds a version to the same document there.

<Callout type="success" title="Tokens stay on the host">
  The Huntaway host keeps the tokens and renews them, and the board only shows whether it's connected and as whom. **Disconnect** forgets the sign-in on the host. To end it on the site too, revoke the grant under **Access**.
</Callout>

Once a document is on the site, share it from its **Share** page there. Answers to form fields and comments are collected on the site, not on the board.

<Details summary="Trying it against a local site">

Run `DOCS_DEV_LOGIN=1 cargo run` in a checkout of dire-kiwi/docs (after building `frontend`, see the [README](https://github.com/dire-kiwi/docs/blob/main/README.md#run-it-locally)), and connect the board to `http://localhost:3000`.

</Details>

## Turning it off, or using the hosted server directly

A project can turn off the board's `docs` server in its settings: deny `mcp__docs` under the project's skills and MCP servers. Its runs then have no `docs` server and aren't told about it.

To have agents publish straight to the hosted site, with feedback and sharing, give the project its own MCP server named `docs` that points at the site's `/mcp`. It replaces the board's. Because a run can't open a browser, use a personal access token (from **Access**):

```json
{
  "type": "http",
  "url": "https://docs.nest.dire.nz/mcp",
  "headers": { "Authorization": "Bearer <token>" }
}
```

<Callout type="danger" title="Keep the token secret">
  A personal access token acts as you on the site. Keep it in the project's server settings on the host, never in a repository.
</Callout>

The agent then has all the hosted tools, including `get_feedback` and `share_document`. Documents belong to the token's user, and their URLs are the site's.
